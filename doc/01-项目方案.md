# 燕云十六声 · 百业组队平台 项目方案

> 版本：v0.8　状态：一期功能规则已收敛，后端待实现。统计累计截至当前周；退会/解散/注销硬删除关联数据；社长未转让退会即解散；管理员与社长可相互指派；换角色取消后重新报名。邮箱/QQ、JWT、站内 SignalR、仅验证邮件范围保持不变；基础数据及服务密钥后续提供。不含附件、头像和文件存储服务。当前仓库仍为交互演示，本平台为非官方玩家工具。
>
> 后端实施设计见 [《03-后端技术方案》](./03-后端技术方案.md)，覆盖模块、数据约束、接口、业务事务、Redis、通知调度、联调、部署和验收；第 16 节记录规则定稿与后续接入资料。完整字段及校验契约见 [《05-一期接口契约》](./05-一期接口契约.md)。

## 1. 项目概述

### 1.1 一句话定位

为《燕云十六声》玩家提供**百业（战队）内部的副本排班协作**工具，并附带玩家展示与招募入口。

### 1.2 核心价值

| 角色 | 痛点 | 平台解决 |
|---|---|---|
| 社长/管理员 | 在群里排班混乱，不知道谁来谁不来，催人靠吼 | 周历排班、报名/取消、排班统计、自动提醒 |
| 成员 | 记不住自己哪天打副本，无法参加时难以同步 | "我的本周"、报名即占位、一键取消、开打前提醒 |
| 散人 | 找不到合适的百业和队友 | 玩家页展示角色流派和在线时段，申请加入百业 |

### 1.3 设计原则

1. **副本排班是核心**，其余板块都为它服务（引流、组织、留存）。
2. **同一份数据，多个视图**：周泳道、成员矩阵、场次详情、我的本周。
3. **手机优先**：玩家大多在手机上看排班和报名。
4. **一期提醒仅站内**：业务事件生成通知记录；账号验证邮件由认证模块独立处理。
5. **不依赖游戏数据接口**：游戏无公开 API，所有资料手动填写。

## 2. 范围与分期

### 2.1 第一期范围（产品与前端交互已确认）

- 账号：邮箱验证码注册 + 邮箱密码登录；保留 QQ 首次授权自动建号与登录，未绑定邮箱的 QQ 账号首次登录须完成绑定验证后才能使用业务
- 游戏角色：创建/编辑角色（角色名、鹅力、多选流派、在线时段及区服）
- 百业：创建、邀请码/链接加入、申请审批、成员管理、三级权限
- 副本：副本模板、北京时间自然周泳道、场次创建、报名/取消、冲突检测、满员候补
- 提醒：仅站内通知（开打前、邀请/审批结果及排班变更）；邮件只用于邮箱注册和 QQ 首次邮箱绑定验证
- 基础页面：我的本周、玩家广场（仅未加入百业的玩家）、百业列表与主页、成员管理及参与情况、通知中心、独立邀请预览、个人设置及申请/邀请记录子页

> 本节确认产品范围，不代表能力已经交付。真实登录、业务接口、持久化、权限、通知及部署另按里程碑完成。参与统计按正式排班计数，保留本周次数和截至当前周的累计排名，含本周未开始正式安排，不计未来周和候补。

### 2.2 后续阶段（尚未纳入一期交互基线）

- 成员矩阵视图、场次详情拖拽排班
- 实际出勤标记与基于实际出勤的统计、本周未参加提醒
- 周模板（保存固定排班、一键复制上周、自动生成下周）
- QQ 机器人推送（推送到百业 QQ 群）
- 公告、百业招募流程扩展（一期保留 recruiting 基础开关）

### 2.3 远期候选

- 玩家广场的流派、时段匹配推荐（玩家广场基础浏览属于一期）
- 微信渠道（企业微信群机器人 / 小程序订阅消息）
- 数据看板（活跃度、出勤趋势）
- 小程序版"我的本周"

### 2.4 明确不做（现阶段）

- 游戏数据自动同步（无接口）
- 游戏内聊天/语音
- 交易、付费功能
- 附件、头像上传/管理、对象存储及文件服务；账号、百业、排班和通知仍需数据库持久化

## 3. 角色与权限

### 3.1 角色

| 角色 | 说明 |
|---|---|
| 访客 | 未登录；需登录后查看平台页面 |
| 散人 | 已登录但不属于任何百业 |
| 成员 | 百业内的普通成员 |
| 管理员 | 百业内的管理者，由社长任命 |
| 社长 | 百业创建者，一个百业只有一位 |

> 一个用户账号可创建多个游戏角色。成员关系绑定在**用户账号**上：同一账号下的所有游戏角色共享一个百业成员身份，一个账号同一时间只能属于一个百业。已加入百业的账号不能申请或接受邀请加入其他百业。每条排班同时关联成员账号和该账号下的具体游戏角色；冲突检测按账号进行，同一账号下的不同角色也不能同时出现在时间重叠的场次中。

### 3.2 权限矩阵

| 操作 | 访客 | 散人 | 成员 | 管理员 | 社长 |
|---|:-:|:-:|:-:|:-:|:-:|
| 登录后浏览玩家广场/百业页 | | ✓ | ✓ | ✓ | ✓ |
| 申请加入百业 | | ✓ | | | |
| 查看本百业排班 | | | ✓ | ✓ | ✓ |
| 报名/取消（自己） | | | ✓ | ✓ | ✓ |
| 创建/编辑场次、指派成员 | | | | ✓ | ✓ |
| 邀请成员、审批申请 | | | | ✓ | ✓ |
| 移出成员 | | | | ✓（仅成员） | ✓ |
| 发布公告（二期） | | | | ✓ | ✓ |
| 任免管理员 | | | | | ✓ |
| 转让社长、解散百业 | | | | | ✓ |
| 修改百业资料与设置 | | | | ✓ | ✓ |

**强制规则：**

- 所有百业相关接口，服务端必须校验"当前用户在该百业的角色"，前端隐藏按钮只是体验优化，不是安全措施。
- 管理员不能移出或任免社长和其他管理员；排班指派/取消不受此目标限制，管理员和社长可相互指派，仍检查时间冲突和容量。
- 所有人可随时退会，社长未先转让时退会即解散百业；退会、解散及注销均明确二次确认。
- 退会/移出硬删除本人在该百业内全部业务关联记录，无冷却，可立即加入其他百业；解散硬删除百业全部关联数据，成员账号/个人角色保留；注销硬删除本人全部数据。删除范围与后台清理见《后端技术方案》8.2–8.3。
- 场次开始后禁止普通报名、指派、换角色/定位、取消及编辑场次；退会/移出/解散/注销清理是明确例外，任何时候允许，已开始场次清理后不递补。实际出勤标记为二期。

## 4. 功能需求

### 4.1 账号与资料

- 一期支持邮箱注册：验证邮箱验证码后设置密码并创建账号，之后使用邮箱 + 密码登录，普通登录不发送邮件。保留 QQ 首次授权建号和已有账号授权登录；微信登录不实现。
- QQ 登录后若没有已验证邮箱，进入强制绑定页；完成邮箱验证码验证才可访问角色、玩家、百业、排班和通知等业务接口。取消或重新打开页面仍须完成绑定，前端跳转不能替代服务端限制。
- 身份通过授权平台、应用标识和平台返回的用户标识确定，不通过昵称匹配账号。
- 百业归属与排班冲突只按平台账号 `user_id` 约束，不识别或限制同一自然人持有多个 QQ 账号；不同 QQ 授权身份不自动合并账号。
- 邮箱为账号验证信息；邮箱注册账号使用它登录，规范化邮箱全平台唯一。已注册邮箱不能直接用于另一个 QQ 账号绑定，不按邮箱自动合并账号。
- QQ 绑定仅验证邮箱，不强制设置密码，仍通过 QQ 登录；一期不额外建设 QQ/邮箱账号合并、关联、找回密码和绑定后改邮箱流程，邮件仅在注册与首次绑定验证使用。
- 个人设置：昵称、默认游戏角色、只读已绑定邮箱，提供“我的申请”“收到的邀请”子页及注销入口；业务通知默认站内，不设置个人渠道开关、免打扰或时段
- 隐私：邮箱、QQ 号默认不公开

### 4.2 游戏角色（GameProfile）

角色资料的核心字段为角色名、鹅力（按战力理解）、流派（支持多选）和在线时段。区服仅有“官服”和“渠道服”两种；坦克/治疗/输出是场次排班定位，不作为角色固定流派。

| 字段 | 说明 |
|---|---|
| 角色名 | 游戏内名称，默认公开展示 |
| 鹅力 | 必填，手动填写，按战力理解，默认公开展示 |
| 流派 | 必填且至少选择一项，支持多选；固定选项由用户提供，默认公开展示 |
| 区服 | 官服 / 渠道服，用于玩家筛选 |
| 在线时段 | 周几 + 时间段，用于匹配 |
| 简介 | 自由文本 |

一期默认展示玩家名（游戏角色名）、鹅力和流派，不提供资料隐藏开关。

默认角色：未手动设置时，使用该账号最早创建的角色（创建时间相同时按 id 排序）；用户可在个人角色列表将本人任意角色设为默认，一个账号只有一个默认角色。角色选择器默认选中该角色，仍允许本场选择其他角色；候补递补使用递补时的默认角色。修改默认角色不改变已有正式排班的角色。若默认角色被删除，在允许删除的前提下清除其默认引用并回退至剩余最早创建的角色；无角色时不能报名或递补。

### 4.3 玩家板块

- 玩家广场：固定仅展示未加入任何百业的玩家，可按区服、流派和在线时段筛选；不提供“是否有百业”筛选项
- 玩家详情页：默认展示游戏角色名、鹅力和流派；一期不公开出勤概况，不提供资料隐藏功能

### 4.4 百业板块

- 创建百业：名称、区服、简介、招募要求
- 百业主页：公开介绍、成员数、招募状态、成员列表（默认展示角色名、鹅力和流派，无隐藏开关）
- 邀请：生成邀请码/链接（可设有效期和次数）；站内直接邀请散人
- 申请：仅未加入任何百业的账号可提交申请，管理员审批；已加入百业的账号不能申请其他百业
- 退出/移出：随时清理该账号在当前百业的关联业务记录，无冷却；社长未转让退会即解散。其他百业无关申请/邀请保留，接受/通过仍重查账号归属
- 成员管理：任免管理员、移出、查看本周与截至当前周的累计排班统计
- 公告（二期）：置顶一条，可附带提醒

### 4.5 副本板块（核心）

#### 4.5.1 概念

- **副本模板（DungeonTemplate）**：副本名、人数上限（最多 10 人）、各定位需求；默认 2 奶妈、1 承伤、7 输出
- **场次（RaidEvent）**：某百业在某天某时段开的一场，关联模板
- **排班（Assignment）**：某场次里的某个成员账号及其选定的具体游戏角色，含该场次的定位和状态

#### 4.5.2 视图

| 视图 | 用途 | 期别 |
|---|---|---|
| 周泳道（竖向，周一至周日） | 总览，每个场次显示三种定位的成员文字标识和空位 | 一期 |
| 场次详情抽屉 | 选择具体角色报名、取消、指派 | 一期 |
| 我的本周 | 固定展示当前北京时间自然周的本人安排，不可切换周次；报名即确认，仅保留取消操作 | 一期 |
| 成员矩阵 | 行为成员，列为周几，看谁排满、谁未参加 | 二期 |
| 拖拽排班 | 在详情里拖拽换人 | 二期 |

#### 4.5.3 报名模式

- **指派模式**：管理员选择成员的具体角色直接安排，成功后立即占位
- **开放报名**：成员选择自己的具体角色报名，成功后即确认并占位，满员进候补
- 两种模式可按场次切换
- 正式排班统一为 `confirmed`，不区分报名、指派和再次确认；`waitlist` 仅表示候补队列，尚未占位。

#### 4.5.4 业务规则

1. **冲突检测**：同一平台用户账号同一时间段不能进入两个场次，即使选择的是该账号下不同游戏角色也不能重复排班。时间区间按 `[开始, 结束)` 判定，前一场结束时间等于后一场开始时间不冲突。
2. **单一百业归属**：一个用户账号同一时间只能属于一个百业；已加入百业的账号不能申请、接受邀请或以其他方式加入第二个百业。
3. **定位限制**：每个定位有人数上限，满员后该定位的报名进入候补。
4. **候补递补**：定位出现空位时，同定位候补按报名时间顺序自动递补并占位，无需再次确认；使用该账号当前默认角色，未手动设置时回退至最早创建的角色。递补前重新校验成员身份、角色归属及账号时间冲突；无法递补时不占位并继续检查后续候补。
5. **取消报名**：不设请假或请假截止规则，仅保留取消操作；开始前取消后删除对应排班或候补记录，立即释放正式占位和时间约束，并触发候补递补。
6. **周展示**：统一按北京时间（Asia/Shanghai）的自然周展示，周一 00:00 至下周一 00:00；一期不依赖游戏周刷新规则。
7. **周模板**：保存一周的排班结构，可一键应用到下周（二期）。
8. **出勤（二期）**：场次结束后管理员可标记实际出勤（到场/缺席/迟到），用于后续统计；不设置请假状态。一期只统计排班，不提供实际出勤标记。
9. **开始后锁定**：以服务端时间判断，场次开始后不可修改场次或排班，前端隐藏操作入口，服务端同样拒绝写入。

### 4.6 提醒模块

集中实施说明见 [《04-通知与提醒方案》](./04-通知与提醒方案.md)：包含站内通知类型及接收人、未读已读接口、定时提醒、内部事件重试和恢复。注册/首次绑定邮件归认证模块。

#### 4.6.1 提醒类型

| 类型 | 触发 | 接收人 | 期别 |
|---|---|---|---|
| 开打前提醒 | 场次开始前 N 分钟 | 已排班成员 | 一期 |
| 邀请/申请/审批结果 | 对应操作发生 | 相关用户 | 一期 |
| 排班变更 | 被指派/被移出/候补递补 | 当事人 | 一期 |
| 本周未参加 | 周中/周末检查出勤为 0 | 对应成员 | 二期 |
| 公告 | 管理员发布 | 全体成员 | 二期 |

#### 4.6.2 渠道

| 渠道 | 难度 | 方案 | 期别 |
|---|---|---|---|
| 站内通知 | 低 | PostgreSQL + SignalR + REST 补查 | 一期唯一业务通知渠道，在线实时刷新 |
| QQ | 中 | 官方 QQ 机器人，推送到百业 QQ 群 | 二期 |
| 微信 | 高 | 个人微信无合规主动推送。可选：企业微信群机器人 webhook、服务号模板消息、小程序订阅消息 | 三期 |

#### 4.6.3 架构

```
业务事务 ──► Outbox ──► 接收人/模板 ──► PostgreSQL 通知记录
                                            │ 提交后
                                         SignalR 提示 ──► REST 查询 ──► 站内列表/角标
场次变化 ──► Quartz 持久化调度 ──► 最新正式排班 ──► 站内开打提醒
邮箱注册/QQ 首次绑定 ──► 认证模块 ──► 验证邮件服务（服务商待提供）
```

- 即时事件：业务变更与 Outbox 在同一 PostgreSQL 事务写入，BackgroundService 消费并生成站内记录；记录创建与事件处理标记同事务提交。
- 定时事件：Quartz.NET 使用 PostgreSQL 持久化调度，在创建场次或调整提醒时安排触发时间；启动及周期性补偿按索引检查待处理任务，不全表轮询。
- 去重：同一用户同一逻辑事件只生成一次站内通知，用唯一键兜底。
- 失败重试：重试 Outbox 内部事件处理，记录次数、下次处理时间及原因；不建设业务邮件队列。
- 一期不保留通知渠道选择或个人通知偏好表，站内记录提交即存在。
- SignalR 只提示本人在线连接刷新，推送失败不回滚通知或重做已提交事务；离线通知保存在数据库，首次连接、重连及重新聚焦通过 REST 补查。已读提交后同步提示本人其他连接。
- 提醒配置：百业仅设置提醒开关和提前分钟数，新场次继承并可在开始前覆盖。变化通过提醒版本与调度补偿生效，生成时检查最新场次和正式排班。

## 5. 数据模型

### 6.4 时间与周的处理

- 数据库统一存 UTC。
- 展示时间统一使用北京时间（Asia/Shanghai），自然周从周一 00:00 开始、下周一 00:00 结束。
- `week_key` 使用北京时间对应的 ISO 自然周编号；后端统一计算并在周接口返回 `week_key, week_start, week_end, timezone`。前端周切换遵循相同规则，以接口返回的边界为准；两端使用同一组跨年、周边界及 UTC 日期与北京时间日期不一致的验证样例，不直接共享 C# 与 TypeScript 运行时代码。
- 游戏周刷新规则不参与一期排班展示或查询；以后确有副本次数统计需求时再确定。

### 6.5 认证与凭证生命周期

邮箱注册验证后设置密码，后续邮箱密码登录不发邮件。QQ 首次授权建号，缺少已验证邮箱时只可读取 `/me`、刷新/退出、完成邮箱绑定或注销本人，业务统一拒绝 `EMAIL_BINDING_REQUIRED`。账号邮箱唯一，不自动合并不同注册来源。

- QQ OAuth 只用于确认 QQ 身份，平台签发自己的访问凭证。QQ access token 与应用密钥仅保存在服务端，不作为平台 JWT 使用。
- Access Token 使用短期 JWT，默认有效期 15 分钟；携带 `sub`（平台用户 ID）、`sid`（会话 ID）、`jti` 和有效期等必要声明。JwtBearer 严格校验签名、允许的算法、issuer、audience 和有效期；签名密钥仅在服务端配置。
- Refresh Token 使用高强度随机字符串，默认会话绝对有效期 7 天；每次刷新轮换凭证，不延长该会话的绝对有效期。Redis 保存用户 ID、会话 ID、凭证哈希、会话族、过期时间及消费/撤销状态，原始凭证不写数据库或日志。
- Access Token 仅保存在前端内存，请求使用 `Authorization: Bearer ...`；Refresh Token 放入 `HttpOnly + Secure + SameSite=Lax` Cookie，限制 Path 为 `/api/v1/auth` 并不设置跨子域 Domain。两个 Token 均不得写入 localStorage/sessionStorage、普通业务 URL 或页面跳转。唯一例外是浏览器 SignalR WebSocket/SSE 连接由 SDK 在 `/hubs/notifications` 请求查询参数中携带 access_token，必须 HTTPS/WSS、服务端严格限定 Hub 路径读取、代理/应用/追踪日志屏蔽该参数；Refresh Token 不进入 Hub 或 URL。
- QQ 授权开始时，将一次性 state 保存至 Redis 并绑定发起授权的浏览器。回调成功后设置刷新 Cookie，并重定向到允许的前端地址；前端调用刷新接口取得 Access Token，再请求 `/me`。重定向地址不得携带 Token。
- 页面重新加载时通过刷新接口恢复登录。刷新前检查平台账号仍为 active；刷新操作使用 Redis 原子校验与轮换，已消费凭证的重放撤销对应会话族。消费记录保留至会话绝对过期，前端协调同页及多标签页的并发刷新，避免轮换竞争。
- 退出时撤销当前刷新会话并清除 Cookie，前端清除 Access Token 和用户缓存。默认已签发的 Access Token 可使用至到期；业务接口继续校验账号状态与当前百业权限。若需退出后所有接口立即失效，再增加每次认证的 Redis 会话检查。
- JWT 不固化百业管理员身份，服务端按当前成员关系鉴权。Refresh Token 失效返回 401；Redis 故障导致授权 state 或刷新流程不可用时返回 503，不绕过会话校验，前端不将其当作凭证失效。
- 同域部署注册、密码登录、刷新和退出接口，校验 Origin 并使用 ASP.NET Core Antiforgery。前端先获取 `/auth/csrf` 凭证，再通过 `X-CSRF-TOKEN` 请求头发送；绑定接口另要求当前账号 Bearer。完整认证流程与验证码作用域见《后端技术方案》6.1。

### 6.6 Redis 职责与数据库一致性

- 一期 Redis 用于刷新会话、一次性授权 state、邮件验证凭证、相关入口限流，以及按需缓存系统副本模板等基础数据。普通缓存可用 `IDistributedCache`，原子操作通过 StackExchange.Redis 实现。
- 设置明确 TTL，一期 Redis 使用 noeviction 策略并监控容量，避免缓存压力随机淘汰登录态；容量耗尽时写入失败须显式处理。Redis 数据丢失可能要求用户重新登录，不导致排班和通知业务数据丢失。
- 周历、成员权限及定位容量一期优先查询 PostgreSQL；是否增加缓存依据实际查询压力决定。Redis 不承担排班一致性，不依赖 Redis 分布式锁保证报名正确性。
- 成员 `UNIQUE(user_id)`、`(event_id, user_id)` 唯一约束由 PostgreSQL 兜底。报名、指派、取消、场次改时和候补递补采用显式事务；按账号检查跨场次冲突，统一锁顺序并处理死锁重试。换角色/定位为取消后重新报名的两个事务，不保留原名额。
- 取消及候补递补在同一事务提交，接口成功返回时占位结果已确定。所有受影响排班写入口复用同一校验路径，单独调用 SaveChanges 不足以保证检查与写入的一致性。
- 调度、Outbox 处理进度及站内通知持久化在 PostgreSQL，一期不另建 Redis 任务队列。API 重启后由 Quartz、事件消费与补偿检查恢复任务。

## 7. API 设计（概要）

REST 风格，前缀 `/api/v1`。统一响应：`{ data, error }`；错误含 `code` 和 `message`。分页用 `cursor` 或 `page/pageSize`。

业务接口使用 Bearer Access Token。QQ 授权端点使用浏览器重定向，刷新与退出使用刷新 Cookie。OpenAPI 是前后端请求、响应及枚举契约来源；后端 DTO 校验独立执行，前端类型生成不替代运行时校验。

注册/登录等认证入口公开，GET /me、首次绑定和本人注销白名单允许 QQ 待绑定账号访问；其余业务查询与写入要求已验证邮箱，未完成返回 EMAIL_BINDING_REQUIRED。

### 7.2 关键接口的行为约定

**`POST /auth/refresh` 与 `POST /auth/logout`**

- 刷新成功返回 `{ data: { access_token, token_type: "Bearer", expires_in: 900 }, error: null }`，新 Refresh Token 仅通过 Set-Cookie 写入。
- 刷新凭证缺失、过期或撤销时返回 HTTP 401 与稳定业务码，清除无效刷新 Cookie；Redis 不可用返回 HTTP 503，前端保留可重试状态。
- 退出撤销当前刷新会话并清除 Cookie，重复退出成功；仅在前端删除 Token 不构成服务端退出。

**`GET /guilds/:id/events?week=YYYY-Www`**
返回该周所有场次，每个场次内嵌 `assignments`（含成员账号昵称、所选游戏角色名、区服、定位和状态），一次请求即可渲染周泳道，避免 N+1。成员文字标识由前端依据名称和账号 ID 生成。

副本周历允许指定 `week` 查询仍存在的历史周；`GET /me/week` 不接受周次参数，始终返回当前北京时间自然周。参与情况统计正式排班，返回本周次数、未排班成员及从当前加入关系至当前周结束的累计排名，包含本周未来安排、不计未来周；退会重入从新关系重新累计，已删除记录不参与统计。

**`POST /events/:eid/assignments`**
1. 请求指定 `action=signup/assign, profile_id, slot_role`；服务端反查角色账号，校验百业成员和本人报名/管理员指派权限
2. 事务内按统一锁协议检查权限、角色归属、场次状态、账号是否已在本场及定位容量
3. action=signup 的本人开放报名定位满员则写入 `waitlist` 并返回候补序号；候补不占时间，递补前重新检查冲突。action=assign 的管理员/社长指派满员返回 CAPACITY_CONFLICT，不自动候补
4. 有空位时校验账号与其他正式排班的完整时间区间冲突，再写入 `confirmed` 占位；无单独确认接口，仅允许场次开始前操作
5. 同事务写 Outbox 排班变更事件，提交后异步处理通知

**`DELETE /events/:eid/assignments/:aid`**
1. 校验权限和服务端时间，仅允许场次开始前取消
2. 删除排班或候补记录；正式排班取消立即释放位置和时间约束
3. 若有同定位候补，按顺序重新校验成员身份和账号冲突，以该账号当前默认角色递补为 `confirmed` 并通知
4. 撤销被取消排班的提醒任务；不保留请假或取消状态

**加入与退出百业**
- 主动退出无冷却、随时清理当前百业个人关联记录；社长未先转让即解散。其他百业无关的申请/邀请保留。解散删除整个百业业务数据，普通成员账号/个人角色保留。
- 审批通过、接受邀请及创建百业须在事务内重查账号无成员关系，UNIQUE(user_id) 防止并发加入两个百业。
- 换角色/定位先取消再重新报名/指派；取消会触发正常递补，重报可能进入候补或失败，名额和候补顺序不保留。注销删除本人账号及全部关联数据，社长未转让复用解散。

### 7.3 实时性

一期站内通知使用 ASP.NET Core SignalR：`/hubs/notifications` 通过 JWT 和已验证邮箱策略鉴权，只向本人在线连接推送 `notifications.changed`（reason 为 created/read/deleted），客户端使通知列表/角标缓存失效并通过 REST 获取真实数据；deleted 另重读 /me 与当前百业上下文。连接正常不固定轮询，断线时每 30 秒降级查询、不可见时暂停，首次连接/重连及重新聚焦补查；Token 到期关闭旧连接，统一刷新后重连，退出/切换账号停止旧连接并清理缓存，注销后禁止向已删除账号投递。

一期单 API 实例不启用 Redis backplane，多实例再接入并配置协商所需会话亲和；反向代理支持 Hub 协商和 WebSocket 长连接。排班页仍用 TanStack Query 重新聚焦刷新及短轮询，二期如需多人同时排班再增加场次变更推送。完整实时契约与恢复设计见《通知与提醒方案》6.1。

## 8. 安全、隐私与合规

- QQ 授权由服务端验证，授权流程校验一次性 `state` 防止登录 CSRF，回调代码不可重复使用；登录接口限流，应用密钥仅保存在服务端。
- 邮箱注册和 QQ 首次绑定须验证邮箱；未完成 QQ 绑定的账号服务端限制业务访问。密码使用框架安全哈希，不存明文，不通过邮件发送密码；验证码限定用途、邮箱与目标账号。
- 全站 HTTPS；刷新 Cookie 按 6.5 配置 HttpOnly、Secure、SameSite 和路径限制；Token、授权码和验证凭证不得出现在日志中。
- 后端所有写接口通过 C# 请求 DTO 校验输入格式，业务服务独立执行权限与业务规则；前端可按需使用 Zod 做表单校验，两端不直接共享校验代码。用户文本安全渲染，刷新和退出接口实施 CSRF 防护。
- 权限校验在服务端，按"当前用户账号 → 百业成员关系"链路校验，禁止仅靠前端。
- 邮箱、QQ 号、手机号默认不公开，公开字段白名单输出。
- 邀请码可撤销、有有效期和次数上限，防止被刷。
- 敏感操作写审计日志。
- 在国内服务器对外提供服务，需要**域名备案**；如涉及用户账号和个人信息，留意个人信息保护相关要求，提供隐私政策和注销账号的途径。
- 页面和素材：不使用游戏官方的图标、立绘、Logo，页脚标注"非官方玩家工具，与游戏运营方无关"。
