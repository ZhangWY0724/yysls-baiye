## 1. 实施目标与范围

一期目标是让现有前端所有业务操作接入真实接口，建立可持久化、可鉴权、可并发操作、可恢复通知任务的服务端。

| 业务范围 | 一期后端交付 |
|---|---|
| 账号 | 邮箱验证码注册/密码登录、QQ 建号/登录及首次邮箱绑定、JWT/刷新、退出、状态校验 |
| 个人设置 | 昵称、默认角色、只读已绑定邮箱、申请记录/撤回、收到的邀请、账号注销 |
| 游戏角色 | 创建、编辑、列表、删除规则、流派与区服校验 |
| 玩家 | 散人列表与详情，按区服、流派、在线时段筛选 |
| 百业 | 创建、列表、主页、资料设置、成员列表、退出、社长转让、解散 |
| 招募协作 | 邀请码、定向邀请、申请、审批、撤回、拒绝和撤销 |
| 成员管理 | 任免管理员、移出成员、参与情况统计 |
| 副本 | 系统/百业模板、场次管理、周历、详情、本人本周安排 |
| 排班 | 报名、指派、取消后重新选择角色/定位、账号级冲突、定位容量、候补递补 |
| 提醒 | 仅站内、开打前提醒、未读/已读、内部事件重试与补偿 |
| 工程保障 | OpenAPI、数据库迁移、审计、日志、测试、容器部署、备份恢复 |

实际出勤标记、成员矩阵、拖拽排班、周模板、公告、QQ/微信推送属于后续阶段。一期统计不能宣传为实际到场统计；百业页面现有招募状态展示与后续招募能力的边界见第 16 节。

附件、头像功能、文件上传下载及对象存储不纳入本项目方案，不保留对应模块、表或接口。前端成员占位可使用名称首字等文字标识；QQ 授权返回的图片信息不进入平台资料模型。PostgreSQL 的业务持久化、Redis 短期状态及通知任务持久化继续保留。

## 2. 技术选型

| 层面 | 采用方案 | 职责及选择原因 |
|---|---|---|
| Web API | ASP.NET Core / .NET 10 LTS + Controller | 开发者熟悉 .NET；统一 HTTP、校验、认证和错误处理 |
| 数据访问 | EF Core + Npgsql | 常规 CRUD、投影查询、迁移；必要时使用参数化 SQL |
| 主数据库 | PostgreSQL 16 | 业务事务、关系约束、部分索引、JSONB 与统计 |
| 短期状态 | Redis + StackExchange.Redis | 刷新会话、OAuth state、验证凭证、分布式限流和按需缓存 |
| 调度 | Quartz.NET + PostgreSQL 持久化 | 开打前触发、任务重排、重启恢复 |
| 异步处理 | Outbox + BackgroundService | 业务事件转站内记录、调度补偿，不包含邮件队列 |
| 实时通知 | ASP.NET Core SignalR + 前端 @microsoft/signalr | 向本人在线连接提示通知变更，REST 获取列表和未读数 |
| 输入校验 | 请求 DTO + 内置校验 | 字段格式校验；复杂字段规则按需引入 FluentValidation |
| 认证 | 邮箱密码 + QQ OAuth + JwtBearer | 框架 PasswordHasher，QQ 首次未绑定邮箱时业务受限 |
| 契约 | OpenAPI + TypeScript 类型/客户端生成 | C# 与前端之间的接口契约，避免手工重复维护 |
| 日志 | Serilog + 请求 ID/Trace ID | 结构化日志、异常定位、任务追踪 |
| 验证邮件 | IVerificationEmailSender / Resend | 当前仅注册验证；QQ 首次绑定暂缓，不依赖业务通知模块 |
| 测试 | xUnit、WebApplicationFactory、真实 PostgreSQL/Redis 测试环境；Playwright 联调 | 验证事务、权限、接口和浏览器业务闭环 |
| 部署 | Docker Compose + 同域反向代理 | 一期 Next.js、API、PostgreSQL、Redis 部署 |

.NET、EF Core、Npgsql、Quartz 等采用兼容的稳定版本并锁定具体版本。框架版本与依赖更新通过独立验证进入部署，不在启动时自动升级。

一期采用模块化单体；不引入微服务、通用 Repository、完整 CQRS、事件溯源或独立认证服务器。Redis 不负责核心排班一致性，也不额外建设一套 Redis 消息队列。

## 3. 总体架构与工程组织

### 3.1 运行架构

```text
浏览器 / Next.js 客户端
        │ HTTPS，同域
反向代理
        ├─ 页面、静态资源 ── Next.js
        ├─ /hubs/notifications ─ ASP.NET Core SignalR
        └─ /api/v1 ─────── ASP.NET Core
                              ├─ Controller / 认证 / DTO 校验
                              ├─ 业务服务 / 权限 / 事务
                              ├─ EF Core / PostgreSQL
                              ├─ Redis 短期状态
                              └─ Quartz + BackgroundService
                                   ├─ Outbox 消费
                                   ├─ 调度与发送任务
认证模块 ── IEmailVerificationSender ── 用户稍后提供的邮箱服务商
```

浏览器业务请求直接进入 ASP.NET Core，不要求经过 Next.js BFF。SSR 若以后需要访问受保护业务数据，再单独设计服务端凭证转发；不能把浏览器内存 JWT 当作 Next.js 服务端已有凭证。

一期后台处理器与 API 同进程运行，处理业务事件及站内提醒；验证邮件只在认证请求中以短超时调用，不建设发送后台。以后独立 Worker 时复用模块，不重写业务规则。

通知在 PostgreSQL 事务提交后通过 IHubContext 提示本人在线连接刷新；SignalR 不替代持久化、Outbox 或 REST 查询。一期后台与 Hub 同进程，后续独立 Worker/多实例时再设计跨进程推送和 backplane。

| 模块 | 主要职责 | 输出或依赖 |
|---|---|---|
| Auth | 邮箱注册/密码登录、QQ 授权、首次绑定、Token 与会话 | Users、Redis、IEmailVerificationSender |
| Users / Profiles | 个人资料、默认角色、角色归属，绑定邮箱只读 | 角色 DTO、账号验证状态 |
| Players | 散人筛选与详情的只读投影 | Users、Profiles、Memberships |
| Guilds / Memberships | 百业生命周期、归属、权限、转让 | 成员身份、审计事件 |
| Invitations / Applications | 加入入口及审批状态机 | 复用成员加入服务 |
| Dungeons / RaidEvents | 模板、场次时间/容量/提醒配置 | 排班服务、调度事件 |
| Assignments | 正式排班、候补、取消、冲突与递补 | Outbox、排班结果 |
| Participation | 本周及累计排班统计 | 只读聚合，不修改排班 |

## 4. 全局数据与接口约定

### 4.1 类型、时间与枚举

- 主键统一 UUID，后端生成 UUID v7；C# 使用 Guid，JSON 使用字符串，前端不将 ID 转成数字。
- 数据库字段 snake_case，API 字段 snake_case；后端序列化与 OpenAPI 保持一致。
- 数据库存 UTC `timestamptz`；后端时间统一 UTC 值。JSON 时间使用带偏移的 ISO 8601，响应优先 `Z`；拒绝没有时区的场次时间。
- `week_key` 为北京时间 ISO 自然周，周一 00:00 至下周一 00:00；周接口返回 `week_key, week_start, week_end, timezone, server_time`。
- 区服 API 值使用 `official / channel`；定位 `tank / healer / dps`；权限 `owner / admin / member`；排班 `confirmed / waitlist`。展示名称由前端映射，不把中文展示名当主键。
- 数据库存枚举字符串并添加 CHECK，OpenAPI 输出字符串枚举。角色流派使用稳定代码，由服务端字典定义，前端读取选项。
- 默认角色统一按本人手动默认引用，否则按 `created_at, id` 获取最早未删除角色。该规则只有一个后端实现入口。

### 4.2 响应、错误与分页

```json
{
  "data": null,
  "error": {
    "code": "ACCOUNT_TIME_CONFLICT",
    "message": "该账号已有时间重叠的排班",
    "details": { "conflicting_event_id": "UUID" },
    "trace_id": "请求追踪标识"
  }
}
```

成功响应为 `{ data: ..., error: null }`，接口同时使用真实 HTTP 状态码。授权跳转与健康检查不强制包装成业务 JSON。

| HTTP | 典型业务码 | 前端处理 |
|---|---|---|
| 400 | VALIDATION_FAILED、INVALID_WEEK、VERIFICATION_CODE_INVALID | 标记字段或参数 |
| 401 | TOKEN_EXPIRED、REFRESH_TOKEN_INVALID、INVALID_CREDENTIALS、ACCOUNT_NOT_FOUND | 仅业务请求刷新一次；密码登录/刷新自身失败不递归刷新；注销账号不存在则清理登录态 |
| 403 | PERMISSION_DENIED、ACCOUNT_DISABLED、EMAIL_BINDING_REQUIRED | 提示无权限或进入首次绑定，不靠刷新提升权限 |
| 404 | RESOURCE_NOT_FOUND | 不返回无权访问资源的详细信息 |
| 409 | ACCOUNT_TIME_CONFLICT、ALREADY_IN_GUILD、EVENT_STARTED、CAPACITY_CONFLICT、VERSION_CONFLICT、EMAIL_ALREADY_IN_USE、EMAIL_ALREADY_BOUND | 展示冲突原因并刷新相关查询 |
| 429 | RATE_LIMITED | 返回 Retry-After |
| 503 | AUTH_STATE_UNAVAILABLE、REFRESH_STORE_UNAVAILABLE、VERIFICATION_EMAIL_UNAVAILABLE | 可重试，不误判登录失效或验证成功 |

候补是成功结果，返回 `status=waitlist` 和同定位候补序号；不以 HTTP 错误表示进入候补。

一期普通列表用 `page/page_size`，默认 20，最大 100，稳定排序增加 ID 兜底；通知与长历史列表使用 `cursor/limit`。周历一次取整周，不分页、不逐场请求名单。不得返回无限成员/通知历史或后台异常堆栈。

### 4.3 幂等与版本

- 创建百业、创建场次、审批通过、接受邀请和报名支持 `Idempotency-Key`。PostgreSQL `idempotency_records` 按用户、操作和 Key 唯一，保存请求哈希、完成响应及过期时间；与业务写入在同一事务完成。
- 相同 Key、相同请求返回已完成结果，不重复发通知；相同 Key、不同请求返回 409。并发同 Key 由数据库唯一约束与锁处理，失败事务不留下永久占位。成功记录默认保留 24 小时。
- Redis 不能替代这些跨业务事务的幂等记录。前端网络超时不盲目重试写操作，显式重试复用原 Key。
- 场次、百业设置等可编辑实体使用显式 bigint `version`，EF Core 配置并发检查；更新请求携带 `expected_version`，陈旧修改返回 VERSION_CONFLICT。不是所有字段变更都需要影响提醒版本，提醒另有 `reminder_version`。

## 5. 数据模型、约束与索引

基础字段沿用项目方案第 5 节，以下补齐后端实现所需字段及约束。所有引用有 FK，常规业务实体有 `created_at, updated_at`；审计/事件等追加记录可只保留发生时间。

| 表 | 核心字段与补充 | 约束/索引 |
|---|---|---|
| users | nickname、email、normalized_email、email_verified_at、password_hash 可空、default_profile_id、status | normalized_email 非空部分唯一；QQ 待绑定邮箱可空，邮箱注册 password_hash 必填 |
| auth_identities | user_id、provider、app_id、open_id | UNIQUE(provider, app_id, open_id)；不按昵称合并账号 |
| game_profiles | user_id、name、server、power、styles、online_slots、bio、deleted_at | UNIQUE(id, user_id) 供复合 FK；power 非负且保留 4 位小数（numeric(12,4)）、styles 非空；角色名不设全平台唯一约束 |
| guilds | owner_user_id、name、server、intro、recruit_requirements、recruiting、提醒配置、version | 区服 CHECK；提醒分钟数边界校验；解散硬删除 |
| memberships | guild_id、user_id、role、joined_at | UNIQUE(user_id)；guild_id WHERE role='owner' 部分唯一；(guild_id, joined_at)，退会硬删除 |
| invitations | guild_id、type、code_hash、target_user_id、expires_at、max_uses、used_count、status、created_by | code_hash 唯一；计数非负且 used_count <= max_uses；(guild_id, status)、(target_user_id, status) |
| invitation_acceptances | invitation_id、user_id、membership_id | UNIQUE(invitation_id, membership_id)，成功使用记录，事务内写入；不额外限制退会后重用仍有效的邀请码 |
| applications | guild_id、user_id、message、status、handled_by、handled_at | (guild_id, user_id) WHERE status='pending' 部分唯一；(guild_id, status, created_at) |
| dungeon_templates | guild_id 可空、created_by 可空、名称、定位需求、default_duration_min、archived_at、version | 定位各非负，需求总数 1..10，时长 >0；系统模板只能读取 |
| raid_events | guild_id、template_id、created_by、title、template_name_snapshot、starts_at、duration_min、week_key、signup_mode、定位需求快照、status、提醒配置、version、reminder_version | (guild_id, week_key, starts_at)、(starts_at)；时长/容量 CHECK |
| assignments | event_id、user_id、profile_id、membership_id、slot_role、status、assigned_by、created_at | UNIQUE(event_id, user_id)；(profile_id, user_id) 复合 FK；(event_id, status, slot_role, created_at, id)、(user_id, status) |
| notifications | user_id、type、source_event_id 可空、payload、dedupe_key、read_at、created_at | dedupe_key 唯一；(user_id, created_at, id) 未读部分索引；无渠道/邮件投递字段 |
| outbox_events | type、aggregate_id、payload、occurred_at、processed_at、attempts、next_attempt_at、lease_until、error | 未处理且到期部分索引；事件 ID 幂等 |
| audit_logs | actor_id、guild_id、action、target_id、detail、trace_id、created_at | (guild_id, created_at)、(actor_id, created_at)，不存 Token 和完整邮箱 |
| idempotency_records | user_id、operation、key、request_hash、response、expires_at | UNIQUE(user_id, operation, key)，定时清理过期记录 |
| profile_style_options | code、label、sort_order、enabled、updated_at | code 主键，用户后续初始化正式流派字典，不采用演示值 |
| Quartz 持久化表 | Job、Trigger、集群协调等 | 采用 Quartz 的 PostgreSQL 官方表结构 |

`membership_id` 绑定当前成员关系，删除成员时删除其排班；重新加入创建新关系，原记录已删除，累计从新加入重新开始。`waitlist_order` 不作为易漂移的持久字段，候补按 `created_at, id` 稳定排序并计算序号。项目结构已迁移到服务器，正式字典和系统模板待初始化。

notifications、outbox_events、audit_logs、idempotency_records 补充用于清理的 `guild_id`、`event_id`（可空）及 `related_user_ids`（UUID 数组）作用域；业务生成时填充涉及账号，按百业/场次索引及 related_user_ids GIN 索引定位删除，不靠解析文案猜测归属。幂等请求若已删除其作用域，则不再返回旧成功数据。通知 source_event_id 仅追踪，不以删除已消费 Outbox 为由误删无关通知。

### 5.1 关键约束示例

```sql
CREATE UNIQUE INDEX ux_users_normalized_email
ON users (normalized_email) WHERE normalized_email IS NOT NULL;

CREATE UNIQUE INDEX ux_memberships_user
ON memberships (user_id);

CREATE UNIQUE INDEX ux_memberships_active_owner
ON memberships (guild_id) WHERE role = 'owner';

CREATE UNIQUE INDEX ux_assignments_event_user
ON assignments (event_id, user_id);

CREATE UNIQUE INDEX ux_applications_pending
ON applications (guild_id, user_id) WHERE status = 'pending';
```

owner 部分唯一索引只能保证“最多一个社长”，不能单独保证“始终有一个社长”。创建和转让在同一事务维护 `guilds.owner_user_id` 与 owner 成员记录；社长未转让退会即删除百业，不留下无社长百业。

跨场次账号时间冲突和定位人数上限不能仅用上述唯一索引表达；由第 9 节统一锁协议和事务检查保证。不为了排斥约束将时间复制到排班表引入额外同步复杂度。

### 5.2 删除、历史与数据有效性

- 角色删除采用 `deleted_at`。若仍用于未结束的正式排班或候补，拒绝删除并返回引用场次；历史 FK 保留。删除默认角色时清除引用，回退至剩余最早角色。
- 修改角色流派、鹅力不重写历史参与事实；本场角色归属不能改变。历史展示是否需要角色资料快照属于后续需求，一期不据当前资料推导真实出勤。
- 普通取消报名物理删除对应 assignment，审计与 Outbox 记录取消事实；历史排班平时可读，退会/移出/解散/注销时按硬删除规则清理。
- 场次取消保留场次历史，取消前的排班作为只读历史保留，冲突和统计排除 cancelled 场次，撤销待发提醒；不能继续递补。
- 普通模板删除被引用后采用归档，场次创建复制容量和名称快照，模板编辑不改变已有需求；成员离开/解散/注销的专门清理流程可删除模板及关联场次，不复用普通归档接口。
- 退会/移出删除本人当前百业关联记录；解散删除百业全部业务与关联记录；注销删除本人账号和全部关联数据。不保留 left_at/dissolved_at、退出历史或匿名化个人记录，具体边界见 8.2–8.3。
- 在线时段存 JSONB，元素格式固定 `{ weekday: 1..7, start_minute: 0..1439, end_minute: 1..1440 }`，要求开始小于结束，跨午夜拆分，限制数量并去重；不允许任意 JSON。
- 对外只投影角色名、鹅力、流派等公开字段。邮箱、密码哈希、QQ 身份、审核备注不从公开成员 DTO 泄露。

## 6. 认证、安全与权限

### 6.1 认证生命周期

邮箱注册和 QQ 建号共用 users，不按昵称、邮箱自动合并账号。业务登录仍使用 15 分钟 JWT、7 天绝对有效期的随机 Refresh Token。

**邮箱注册与密码登录**

1. 前端获取 `/auth/csrf`，调用 `/auth/email-registration/code`，提交 email；后端限流并创建用途为 email_registration、绑定规范化邮箱的随机 challenge_id 与验证码。
2. Redis 保存验证码哈希、邮箱、用途、到期和尝试次数，不存密码。建议验证码 10 分钟、最多 5 次验证、重发至少间隔 60 秒；参数集中配置。
3. IEmailVerificationSender 同步以短超时发送验证码；供应商失败返回可重试错误，挑战不进入可完成状态，不创建账号。待服务商提供后接入，不建设邮件队列。
4. `/auth/register` 提交 email、password、challenge_id、verification_code。验证码匹配用途/邮箱并原子一次消费后，用框架 `PasswordHasher<User>` 生成带盐密码哈希；PostgreSQL 事务创建用户及已验证邮箱，唯一索引防并发重复注册。
5. Redis 和数据库不能组成分布式事务；消费验证码后数据库失败不保留半账号，必要时重新发送。若账号已提交但登录会话建立失败，可使用邮箱密码正常登录，不能重复建号或绕过验证码。
6. `/auth/login` 只提交邮箱和密码，验证哈希及 active 状态后建立会话，不发送邮件。密码建议 8..128 字符并允许长短语，采用框架安全默认哈希参数及 RehashNeeded 升级；未知邮箱/错误密码/QQ 账号未设置密码统一返回 INVALID_CREDENTIALS，避免区分登录失败原因。

**QQ 建号与首次绑定**

1. QQ state 绑定浏览器、Redis 一次消费；回调验证身份，在事务中创建或获取 users/auth_identities，身份唯一键防重复建号。
2. 建立会话后 `/me` 返回 `requires_email_binding`。email 为空或未验证时强制进入绑定页，服务端业务策略 `VerifiedEmailRequired` 同样拒绝访问，不信任 JWT 中永久固化的“已绑定”声明。
3. 待绑定账号只可读取 `/me`、获取 CSRF、刷新/退出、调用 `/auth/email-binding/code`、`/auth/email-binding` 或本人 `/me/account-deletion`。其他业务查询和写入均返回 HTTP 403 / EMAIL_BINDING_REQUIRED。
4. 绑定验证码用途为 qq_email_binding，同时绑定当前 user_id 和规范化邮箱；不得复用注册验证码、冒用他人 challenge 或通过 PATCH /me 绕过。验证后锁本人账号并事务写入唯一邮箱及验证时间，再解除业务限制。
5. 已绑定账号再次提交绑定返回 EMAIL_ALREADY_BOUND；邮箱已被其他账号使用返回 EMAIL_ALREADY_IN_USE，不自动合并。绑定不强制设置密码，QQ 账号仍通过 QQ 登录；一期不建设账号关联/合并、忘记密码和绑定后改邮箱。

**共同会话规则**

- 注册/密码登录成功返回 Access Token 并设置刷新 Cookie；QQ 回调设置 Cookie、跳回前端后通过 refresh 获取 Access Token，再读 `/me` 决定进入业务还是绑定。
- Cookie 为 HttpOnly、Secure、SameSite=Lax、Path=/api/v1/auth、host-only；Access Token 仅浏览器内存，业务使用 Bearer。
- 注册、密码登录、刷新和退出校验 Origin/Antiforgery；绑定另要求当前待绑定账号 Bearer。Refresh Token 原子轮换、哈希存 Redis，重放撤销会话族，前端协调并发刷新。
- Antiforgery 请求凭证需匹配当前请求身份，切换匿名/已登录身份或账号后重新取得，不能把旧身份凭证用于绑定或退出。
- 业务认证严格校验签名、算法、issuer、audience、有效期、active 状态与最新邮箱验证状态，再执行百业权限。刷新允许待绑定账号继续完成绑定，不能代替业务访问策略。
- 退出登录撤销刷新会话并清除 Cookie；默认旧 Access Token 到期前可能有效，若要求立即撤销再增加 sid 检查。封禁校验账号状态，注销后账号不存在则拒绝访问，不能凭旧 JWT 重建账号或会话。

身份平台 Token、平台 Token、验证码不得出现在普通业务 URL、页面跳转或日志。唯一例外是浏览器 SignalR WebSocket/SSE 连接通过 SDK accessTokenFactory 在 `/hubs/notifications` 请求中携带 access_token；仅允许 HTTPS/WSS，JwtBearer OnMessageReceived 严格限定该 Hub 路径及其子路径，代理/应用/追踪日志屏蔽该参数。Refresh Token 永不进入 Hub 或 URL，Token 均不写 localStorage/sessionStorage。JWT 不携带长期有效百业管理权限。刷新存储故障返回 503，不绕过 Redis 建立会话。

### 6.2 百业权限与资源校验

| 动作 | 普通成员 | 管理员 | 社长 |
|---|---|---|---|
| 本百业周历/详情 | 可读 | 可读 | 可读 |
| 本人开放报名/取消 | 开始前可操作 | 开始前可操作 | 开始前可操作 |
| 场次/模板/设置、审批、邀请 | 不可 | 可 | 可 |
| 指派其他成员排班 | 不可 | 可，含社长/其他管理员 | 可，含管理员 |
| 移出成员 | 不可 | 仅普通成员 | 除本人外可操作；本人退会未转让即解散 |
| 任免管理员 | 不可 | 不可 | 可 |
| 转让/解散 | 不可 | 不可 | 可 |

管理员不能移出、任免社长或其他管理员，但管理员/社长可相互指派和取消排班；这些排班操作仍须校验容量、账号时间冲突及开始前限制。所有人换角色/定位统一取消后重新报名/指派，不提供 PATCH assignment，也不保证原名额或候补顺序保留。退会/移出/解散/注销的删除流程是开始后锁定的明确例外。

所有嵌套资源验证实际归属，例如 event.guild_id 必须等于路由 guild_id，assignment.event_id 必须等于路由 event_id。不能只鉴权路由中的百业而更新另一个百业的资源。本人操作从 JWT sub 确定，指派从 profile 反查 user_id 并验证目标成员身份。

对敏感写操作，事务加锁后再次查询操作者、目标账号状态与有效成员关系，避免权限检查后被撤权却仍写入。草稿仅本百业管理员/社长可见；其他百业用户只能查看百业公开版本信息，不能通过详情接口获取排班名单。

### 6.3 安全与隐私

- 同域部署，CORS 不使用任意 Origin + Credentials；开发环境明确列出本地来源。限制 forwarded headers 的受信代理，认证/限流不信任客户端伪造 IP。
- EF/SQL 全部参数化；自由文本按纯文本保存和安全渲染，不开放任意 HTML。
- QQ 登录、邮箱密码登录、注册/绑定验证码、邀请码设置独立限流，按 IP 和邮箱/账号限制；Redis 故障不绕过限流或验证。所有密码、验证码、身份 Token 不记录日志。
- 邮箱先 trim 并按统一规则规范化为不区分大小写的值，不做供应商特有的去点或去加号处理；验证码限制用途与目标，只有验证完成后写账号邮箱。一期无一般改邮箱和业务邮件能力。
- 注销入口要求本人明确二次确认；任何时候可执行，普通成员先清理成员关联数据，社长未转让则解散百业，再硬删除账号、角色、授权身份、通知和所有关联记录，撤销所有会话。不发送注销邮件。

| GET | /notifications/unread-count | 未读数 | 本人，仅站内有效通知 |

实时端点 `/hubs/notifications` 独立于 `/api/v1`，由 SignalR SDK 负责协商/连接，不计入 REST 操作数量。Hub 使用 JwtBearer + VerifiedEmailRequired；IUserIdProvider 从已验证 sub 映射唯一 user_id，服务端通过 Clients.User 发送 `notifications.changed`，载荷为 reason=created/read/deleted。客户端不能指定接收用户，Hub 无业务写入/任意群订阅方法。事件使通知列表/角标缓存失效，deleted 另重读 /me 与当前百业上下文；数据经 REST 获取，已注销账号禁止投递。完整连接契约见《通知与提醒方案》6.1，Hub 契约独立维护，不由 OpenAPI 自动生成。

实际出勤接口 `/events/{event_id}/attendance` 归入二期，不纳入一期 API 验收；不能因为原概要列出了路径就提前实现。

### 7.6 关键请求与响应 DTO

以下字段进入 OpenAPI 契约；字段长度、数值上限等通过配置和 DTO 校验固定，客户端不能直接提交数据库实体。写入的 actor_id、user_id、创建时间等审计信息由服务端生成。

| 操作 | 关键输入 | 返回内容 |
|---|---|---|
| 注册验证码 | email | challenge_id、expires_in、resend_after；供应商成功才受理 |
| 邮箱注册 | email、password、challenge_id、verification_code、nickname 可选 | 账号、Access Token 与刷新 Cookie |
| 密码登录 | email、password | Access Token 与刷新 Cookie；不发送邮件 |
| QQ 绑定验证码/提交 | email；提交另含 challenge_id、verification_code；user_id 从 JWT 获取 | 挑战或绑定成功，重新获取 /me |
| 创建/编辑角色 | name、server、power、styles、online_slots、bio | profile_id、公开资料及默认状态 |
| 修改 /me | nickname、default_profile_id（只允许这些白名单字段） | 本人资料、默认角色及验证状态 |
| 创建百业 | name、server、intro、recruit_requirements | guild_id、version、owner membership |
| 处理申请 | decision=approved/rejected、expected_status=pending | application 状态、审批时间；通过时返回成员关系 |
| 创建邀请 | type=code/direct、target_user_id（direct 必填）、expires_at、max_uses（code） | invitation_id、可用状态；code 类型仅创建时返回 code 与前端邀请链接 |

| 模板配置 | name、need_tank、need_healer、need_dps、default_duration_min | template_id、version |
| 创建场次 | template_id、title、starts_at、duration_min、signup_mode、status=draft/published、定位需求、note、reminder 配置 | event_id、版本与完整场次 DTO；省略容量/提醒字段时继承模板/百业快照 |

整周列表可用于首次打开抽屉，详情接口用于补齐及刷新最新状态。返回 `ends_at` 由 starts_at + duration_min 计算，不把前端固定的“预计 90 分钟”作为真实场次时长。

## 8. 百业归属、邀请与审批事务

### 8.1 创建与加入

- 创建百业：事务内锁定创建账号，确认无有效成员关系，创建 guild 和 owner membership，写审计；唯一索引兜底。不能先提交百业再另行创建社长。
- 申请：检查申请人当前为散人及百业可接收申请，写 pending；一个账号可申请多个百业，但同百业仅一个 pending。
- 审批通过：事务内重新校验操作者权限、申请状态、申请账号无归属，创建 membership，变更 application，写 Outbox；并发通过不同百业只能成功一次。
- 邀请接受：同一事务锁定邀请码/邀请，核验有效期、次数、状态及目标本人，加入成员、写 acceptance、增加 used_count、产生事件。最后一次使用不能被并发超额消费。
- 审批拒绝、撤回、拒绝邀请、撤销邀请均按状态条件更新；重复动作走幂等响应，不重复生成通知。

可重复使用的邀请码在未撤销/未过期时保持 pending，达到次数上限由计数判定不可用；定向邀请接受后为 accepted。不能将一次使用的邀请码整体标记 accepted 而提前阻止其他合法使用。邀请码使用密码学安全随机数生成，建议至少 128 位熵；代理与应用访问日志均对路径中的邀请码脱敏。

### 8.2 转让、退出与解散

- 转让：锁定百业和参与账号，重新校验 owner、目标有效身份；先将原 owner 调整为请求指定的 member/admin，再将目标设为 owner，更新 owner_user_id、版本和审计，整个事务提交。
- 退出与移出：任意时间删除当前成员关系、该账号本百业的全部正式/候补排班、申请、邀请使用记录、本人创建/处理的关联业务数据以及相关通知、审计、Outbox 和幂等记录。账号、游戏角色和其他百业无关申请保留。普通成员被移出的权限保持原规则。
- 清理本人创建的百业模板、场次和邀请时，连同引用模板的场次、场次内所有排班/提醒、邀请接受记录一起删除；受影响的其他成员排班会随关联场次删除，但不能因此删除其他账号/角色或百业中无关资源。退会/移出前的确认界面必须说明此影响。
- 清理个人关联时，凡包含其审批/指派等引用的记录均按作用域纳入清理，不能残留姓名快照或通过审计/通知继续保留个人历史。剩余百业的版本递增，统计即时按剩余记录重算。
- 仍存在且未开始的场次，释放正式名额后按同定位队列递补；已开始/结束场次只删除关联记录、不递补。退会和删除本身不受开始后锁定限制。
- 解散：验证当前 owner、版本和二次确认信息；任意时间硬删除百业、成员关系、百业模板、场次、全部排班、申请/邀请/接受记录及相关通知、审计、Outbox/幂等记录，撤销全部 Job。成员账号和个人角色保留，成为散人。
- 社长主动退会时可事先转让后按普通退出执行；没有转让则要求 confirm_dissolve=true，直接复用解散流程，不强制用户先转让。不创建 membership.removed/guild.dissolved 持久通知重新保留已删除业务信息。
- 原百业数据已删除，旧链接/通知目标返回 404；当前账号身份仍存在时读取 /me 得到新归属。本人其他百业的待处理申请/邀请不因退出当前百业自动通过，仍重新检查归属。

### 8.3 注销与后台清理一致性

- 本人提交 confirm_user_id + confirmation=DELETE；按统一锁协议锁相关百业及账号，重读当前归属；普通成员执行成员清理，社长未转让执行解散。随后删除本人其他申请/邀请、授权身份、全部角色（含软删除角色）、通知、审计、Outbox/幂等及 users，不保留匿名化副本。只删除本人关联，不扩散删除其他人的账号和角色。
- 业务删除在一个 PostgreSQL 事务完成，FK 按资源所有权配置 CASCADE/RESTRICT，交叉引用由清理服务按固定顺序删除；不能对 users 的任意外键盲目 CASCADE 到整个百业。全量删除字段和清理清单由集成测试核对。
- Redis 不加入数据库事务：注销提交后通过用户级会话索引撤销全部会话，不使用 KEYS 扫描。当前无持久化技术清理队列；Redis 故障时账号数据库校验立即拒绝旧 Token，残留技术键最长 7 天 TTL 到期。Quartz 为周期任务，不保留每场 Job。
- Job/Outbox 消费与删除遵循相同百业锁协议，生成通知前重查账号、成员和业务资源；删除提交后即使旧任务尚未清理也只能安全跳过，不能按旧 payload 重新创建记录。调度补偿也负责删除孤立 Job。
- 注销后刷新与 HTTP 认证以账号不存在判失败，所有旧 JWT 不得继续访问；Hub 在建立连接和推送前查询账号存在/状态，注销后禁止向旧连接投递，客户端及其他标签页停止连接。Redis 清理失败不得使已删除账号重新可用，技术清理重试不重建账号。
- 在线数据按硬删除规则执行；备份包含删除前快照，按 7–14 天保留周期过期，不能宣称现存备份即时擦除。恢复前用备份快照之外独立保留的技术删除清单重放清理，核对通过才能对外开放；清单只带目标ID/清理范围、最长与备份保留期相同，不带个人资料或提供用户历史查询。

## 9. 排班并发、状态与事务

### 9.1 统一锁协议

一期业务写入与通知任务使用显式 Read Committed 事务和同一 PostgreSQL 事务级 advisory lock（72420261013），等待锁后重新查询账号、权限和业务状态。锁释放随事务完成，无外部邮件请求持锁，提交后再发送实时提示。

该实现将业务写入整体串行，优先保障定位容量、同账号跨角色冲突以及硬删除与通知生成的一致性。当前单 API、小队排班规模下保持简单；后续若压测显示瓶颈，再按百业、账号和场次细化锁，不能直接移除并发控制。

### 9.2 报名与指派

1. 校验 DTO，读取 event 的真实百业归属，开启事务并按协议加锁。
2. 重新检查账号 active、操作者权限、目标有效成员、角色属于目标、场次已发布且未取消、当前时间早于 starts_at。
3. open 模式允许本人报名；assign 模式仅有权限管理员/社长指派，不能通过伪造 user_id 绕过。
4. 检查 UNIQUE(event_id, user_id)，重复报名不产生第二条记录。
5. 正式排班重叠条件：`existing.starts_at < target.ends_at AND target.starts_at < existing.ends_at`，时间区间为 `[开始, 结束)`；排除候补、草稿和取消场次。账号下不同角色同样参与检查。
6. 目标定位有空位则写 confirmed；定位已满的开放报名写 waitlist。候补不占时间，允许其存在其他正式时间冲突，递补时重新检查；这一点澄清原接口概要“先检查冲突再判断满员”的顺序歧义。
7. 指派不能突破容量，定位已满返回 CAPACITY_CONFLICT，不自动候补；本人开放报名满员才进入候补。请求增加 action=signup/assign，区分管理员本人报名和其指派行为，前端明确显示操作模式。
8. confirmed 写入绑定本场 profile_id，修改默认角色不会影响它；waitlist 保存并在递补时使用报名所选角色，默认角色修改不静默更换排班。
9. 同事务写 Outbox 及必要审计/幂等响应，提交后返回 assignment_id、status、waitlist_position、event_version。后台仅生成站内通知，不发送邮件。

### 9.3 取消与自动递补

1. 按锁协议读取正式名单和同定位候补，检查权限及开始前限制。
2. 删除本人/目标 assignment；仅取消候补不影响容量。
3. 正式排班释放后，按 `created_at, id` 顺序检查同定位候补；重新验证当前成员关系、账号状态、所选角色与跨场次冲突。
4. 所选角色无效、已退会或有冲突的候补不占位，继续检查后续候补；保留尚有可能有效的候补供之后重试，已无成员身份的记录按成员离开策略清理。
5. 合法候补更新为 confirmed，保留报名时所选 profile_id；一旦补满当前定位停止递补。
6. 取消、递补、提醒变更事件在一个事务提交；接口返回时位置确定，不交给后台任务决定最终占位。

换角色/定位统一先 DELETE 取消，再 POST 重新报名或指派，是两次独立业务操作。取消成功即可触发候补递补，重新报名可能候补/满员/失败，原位置和候补顺序不保留；前端先说明这一点，再执行取消，取消失败不得继续报名。不提供 PATCH 排班或变相原子换位接口。

### 9.4 修改场次与生命周期

- draft → published；draft/published 在开始前可取消。进行中由时间推导，不依赖定时任务及时切换状态来实现锁定；到结束时间后可标记 finished。
- starts_at、duration_min 改变时，锁所有正式排班账号，逐个检查新时段与其他正式场次的冲突。任何一个冲突则整体拒绝，保留原场次与排班。
- 减少定位容量不能低于已确认人数；不能自动挤掉成员。增加容量后检查对应候补，是否自动递补采用与取消一致的规则。
- 修改模式不改变已有 confirmed/waitlist 记录；open→assign 后停止本人新报名，但仍可在开始前取消本人安排。
- start 时间或提醒配置变化递增 reminder_version；旧任务失效，Outbox 驱动重排。
- 普通报名、指派、取消、修改和取消场次开始后拒绝 EVENT_STARTED；退会/移出/解散/注销的硬删除是例外，可在任意时间清理，已开始场次不触发候补递补。未被删除的记录可读，实际出勤标记属二期。

## 10. Redis 设计

| Key 示例 | 内容 | 生命周期与原子性 |
|---|---|---|
| yanyun:{env}:auth:state:{hash} | 浏览器关联、回调目的、到期时间 | 建议 5 分钟，原子一次消费 |
| yanyun:{env}:auth:session:{sid} | user_id、会话族、当前凭证哈希、绝对到期 | 最长 7 天，轮换不延长绝对期限 |
| yanyun:{env}:auth:consumed:{sid}:{hash} | 已消费刷新凭证 | 保留至会话绝对到期，重放检查 |
| yanyun:{env}:email:challenge:{challenge_id} | purpose、normalized_email、user_id（绑定时）、验证码哈希、次数、可完成状态 | 建议 10 分钟，一次消费；注册与绑定不能串用 |
| yanyun:{env}:limit:{operation}:{subject} | 计数与窗口 | 按操作配置，Lua 原子计数+过期 |
| yanyun:{env}:cache:dictionary:{version} | 流派、区服字典 | 按版本更新，建议 1 小时 |
| yanyun:{env}:cache:system-templates:{version} | 系统模板 DTO | 修改后失效，建议 10 分钟 |

以上 TTL 中授权与验证码为建议默认值，集中配置。Redis 一期单实例，noeviction，设置容量告警与访问认证，不公开网络端口。环境前缀隔离开发/测试/生产，但前缀不等于安全隔离，生产独立部署。

使用单例 ConnectionMultiplexer，不按请求建立连接；短超时和明确故障响应。Redis 重启/丢失可能导致重新登录或重新发验证凭证，不损坏业务数据。会话族等多 Key 原子脚本在一期单实例执行；以后迁移 Cluster 时需要 hash tag 保证同 slot。

周历、容量、成员权限、参与统计一期直接查 PostgreSQL。可淘汰缓存以后需要独立实例时再拆分，不为了通用缓存牺牲会话可靠性。

## 11. 查询模型与统计口径

### 11.1 前端所需查询

- `/me` 输出当前账号、default_profile、membership（含 guild_id/role）和验证状态，作为登录后上下文入口。
- 周历先取场次，再批量投影排班与所选角色，使用有限次数查询组合，不启用 Lazy Loading，避免按场次/成员产生 N+1。
- 详情包含场次标题、模板名称快照、时间、定位需求及人数、confirmed 名单、按定位候补、本人 assignment、can_* 操作提示。
- 我的本周查询按当前北京时间周起止过滤本人正式/候补记录，不接受客户端切到其他周；显示所选角色、排班状态和场次状态。
- 玩家广场用有效 membership 的 NOT EXISTS 过滤；区服、流派和在线时段均在数据库执行，分页前过滤，不先读取全量后在内存筛选。
- 百业公开主页只返回公开角色和近期场次摘要；不复用内部周历 DTO 导致名单泄露。

### 11.2 一期参与统计口径（已确认）

- 名称使用“已排班次数”，按当前成员、未取消且 status=confirmed 的 assignment 去重 event_id 计数，候补不计；不暗示真实到场。
- 本周按场次 starts_at 所在北京时间自然周计算，包含本周已结束和尚未开始的正式安排，不包含下周及更远的排班。固定当前周，不开放统计切周参数。
- 未排班成员为当前成员、本周计数为 0 的账号。
- 保留累计排名，按当前百业当前成员关系从 joined_at 至当前周结束的正式排班计算，`starts_at < week_end`；退会时旧记录全部删除，重新加入累计从新 joined_at 开始。清理后不保留退出成员排名。
- 响应包含 `basis=confirmed_assignments, week_key, week_start, week_end, timezone, server_time, cumulative_cutoff=week_end, includes_future_in_current_week=true`；每个成员返回本周次数、累计次数和稳定名次，按累计次数降序、joined_at/user_id 稳定排序，在分页前计算全局名次。支持 page/page_size 和 unassigned_only，当前页返回对应未排班账号，不无限返回全量成员。二期实际出勤独立统计，不覆盖一期排班数字。

统计用 SQL 聚合与左连接包含 0 次成员；相同次数稳定排序。不引入单独计数缓存表，避免取消、转让和重入后计数漂移。

## 12. 通知、事件与调度

完整站内接收人、数据及接口见 [《04-通知与提醒方案》](./04-通知与提醒方案.md)。一期仅站内中心、未读角标、已读和开打前提醒，移除业务邮件与渠道选择；注册/绑定验证码不进入通知模块。

### 12.1 事件清单

| 事件 | 产生位置 | 消费动作 |
|---|---|---|
| application.created / handled | 申请/审批事务 | 通知有权处理者或申请人 |
| invitation.created / accepted / declined | 邀请事务 | 定向邀请及处理结果通知 |
| assignment.created / removed / promoted | 排班事务 | 当事人通知、开打前任务更新；换角色通过取消/重报表达 |
| raid.changed / cancelled | 场次事务 | 通知受影响正式及候补账号，周期扫描读取最新设置 |
| guild.owner_transferred | 成员事务 | 转让通知 |
| 关联硬删除 | 删除事务 | 清理相关 Outbox/通知，提交后尽力推送刷新提示；Redis 会话按账号索引撤销 |

只实现明确接收人规则，业务事件 ID 为去重来源，不建设通用规则引擎或渠道适配器。

### 12.2 Outbox 与站内记录生成

1. 业务事务写 Outbox，持久化 Quartz 周期任务每 10 秒在统一事务锁内消费到期记录，每批 100 条。
2. 记录创建与 processed 标记同事务提交，dedupe_key 防重复；站内记录提交即存在，不设投递状态。
3. 调度使用 PostgreSQL 持久化周期 Job，每轮按最新业务数据判定，重启后补查未开始场次。
4. 单条无效负载记录次数和指数退避，最长 1 小时；数据库故障整轮回滚，下轮重试。当前不使用租约，通知表不保留邮件处理字段。
5. 无效负载记录脱敏 ID 供运维修复，业务已经提交不回滚；注册邮件短超时同步调用，不建立业务邮件队列。

新通知（包括 Quartz 提醒）及已读更新事务提交后，短超时调用 IHubContext 推送 `notifications.changed` 到本人所有在线连接。推送失败不能回滚通知、重置 Outbox processed 或重复执行已提交的生成事务；仅记录脱敏结果，漏提示通过首次连接、重连、网络恢复及重新聚焦时 REST 补查恢复。不增加消息确认、重放队列或推送状态表，发送成功不表示用户已读。

### 12.3 开打前提醒

- Quartz 在 PostgreSQL 持久化周期任务，不为每场保存独立 Job；执行时从数据库读取当前到期场次和正式名单。
- 百业默认开关/提前分钟被场次创建时继承，可单场覆盖，无渠道选择和个人通知偏好。
- 生成前按统一事务锁协议重查场次未取消/尚未开始、成员及正式排班有效；检查和插入站内记录同事务。
- 改时/关闭/取消通过实时场次数据生效；晚于提醒时间但未开始的新报名在下一轮补查，固定 event_id/user_id 去重，已生成不重复。
- 启动和周期扫描按 starts_at 索引分批检查，不补已开始提醒；不保存独立场次 Job。通知平时可读，退会/解散/注销时按关联作用域删除，不能保留已删除业务的摘要。

每个标签页在 `/me` 确认已完成绑定后建立一个通知连接；事件和已读成功均使列表/角标缓存失效，多标签页通过本人推送同步。Hub 设置 CloseOnAuthenticationExpiration=true；前端统一刷新 Token 后重连，首次 start 失败也退避重试，失败/断线期间保留降级轮询。退出/切换账号停止旧连接和重试、取消旧查询并清理缓存，迟到结果核对当前账号。默认旧 JWT 到期前仍可能有效，主动关闭本页连接不等于服务端撤销所有设备。

## 14. 部署、配置与运维

### 14.1 部署拓扑与配置

- Docker Compose 启动反向代理、Next.js、ASP.NET Core、PostgreSQL、Redis；数据库与 Redis 使用持久卷和内部网络，只向外开放 HTTPS 所需端口。
- API 容器无本地会话状态。JWT 签名、QQ 密钥、数据库/Redis/邮件凭证由部署秘密配置注入，不提交仓库。
- Antiforgery 依赖的 Data Protection 密钥持久化；多 API 实例共享该密钥，滚动重启不破坏安全 Cookie。
- 配置按 Auth、Database、Redis、Mail、Scheduling、Realtime、RateLimits 分组，启动时验证必需项；开发使用独立 QQ 应用/回调或仅限测试环境的替身。
- 同域反向代理转发 `/hubs/notifications` 的协商和连接请求，支持 WebSocket Upgrade，配置长连接超时并验证 SDK 回退传输；访问日志及追踪不能保存 access_token 参数。
- EF Core 迁移由单次部署任务显式执行，不让每个 API 实例启动时并发迁移。部署前确认备份，先数据库兼容性迁移再滚动代码；破坏性迁移单独安排。
- 一期单 API 实例，不启用 SignalR Redis backplane；扩展多实例时再启用 backplane 及协商所需会话亲和，同时启用 Quartz PostgreSQL 集群模式，Outbox 保持原子领取，Redis 限流保持共享。Backplane 仅转发在线提示，不保证离线重放；扩大实例数量不能重复生成提醒。

### 14.2 可观测性与恢复

| 项目 | 要求 |
|---|---|
| 健康检查 | /health/live 检查进程；/health/ready 检查关键数据库/Redis连接，不泄露配置 |
| 请求日志 | trace_id、接口、状态码、耗时、必要的用户/资源 ID；屏蔽敏感正文和凭证 |
| 任务日志 | event_id、Outbox ID、通知 ID、内部事件尝试；验证码供应商结果由 Auth 脱敏记录 |
| 业务审计 | 移出、任免、转让、解散、指派/取消/改时；与业务事务一致 |
| 指标 | API P95/错误率、锁等待、Outbox 积压、Quartz Misfire、Redis 内存、注册/绑定验证失败 |
| 数据库备份 | 每日备份，保留 7–14 天，独立备份位置或异机保留；定期执行恢复演练，不引入业务文件服务 |
| 初期恢复目标 | 建议 RPO <=24 小时；RTO 在恢复演练后确定，不以单机部署宣称高可用 |
| Redis 恢复 | 可启用 AOF 辅助恢复，但 PostgreSQL 仍是业务备份核心；丢失会话重新登录 |
| 任务恢复 | Outbox 租约回收、未完成任务重试、Quartz 调度补偿；不能只靠进程内定时器 |
| 数据清理 | 过期幂等记录、已消费凭证；审计/通知保留期按隐私策略确定 |

周历接口沿用 P95 <300ms 目标，在明确数据规模下实测，不将缓存命中作为唯一合格场景。备份恢复、邮件送达与内置浏览器授权是上线验收的一部分。
