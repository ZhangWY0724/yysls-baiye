# 燕云十六声 · 百业组队平台 站内通知与提醒方案

> 版本：v1.5；日期：2026-10-13；状态：站内 REST、Outbox、Quartz 持久化周期任务和 SignalR 已实现并完成真实链路测试。退会/解散/注销删除对应关联记录；Resend 邮件当前只用于注册验证，QQ 首次绑定暂缓。
>
> **v1.6（2026-10-14）实现调整**：去掉 Outbox 与 Quartz。业务通知在业务事务内直接写入 notifications 表，提交后推送 SignalR 变更提示；开打提醒由 API 内的 ReminderService（BackgroundService）每 15 秒扫描到期场次写入，去重键 `reminder:{场次}:{用户}` 保证重启和多实例不重复。下文涉及 Outbox、Quartz 的描述以此为准。
>
> 依据：[项目方案](./01-项目方案.md)、[后端技术方案](./03-后端技术方案.md)。本文件仅定义业务通知；账号验证邮件归属 Auth 模块，不进入通知中心或业务调度。

## 1. 一期范围

| 能力 | 实现 |
|---|---|
| 业务通知 | 申请、邀请、审批结果、报名/候补/递补、场次变化生成站内记录 |
| 开打前提醒 | 开始前 N 分钟通知当前正式排班成员，仅站内 |
| 通知中心 | 本人分页列表、未读数、单条/批量/全部已读、内部跳转 |
| 实时更新 | ASP.NET Core SignalR 推送本人通知变更提示，前端通过 REST 刷新列表和未读数 |
| 提醒配置 | 百业默认开关和提前分钟数，新场次继承并可覆盖 |
| 可靠性 | PostgreSQL Outbox、唯一去重键、Quartz 持久化、重启补偿 |

移除业务邮件、邮件通知开关、渠道选择、通知邮件模板、外部投递队列和投递状态；一期所有业务通知默认进入站内中心，不保留个人渠道偏好表或接口。附件、头像和文件服务继续不包含。

在线用户通过 SignalR 即时刷新通知；离线期间通知保存在数据库，下次打开平台通过接口读取。一期不提供浏览器系统推送。QQ 群、微信、公告通知、本周未参加提醒按后续分期。

## 2. 通知类型与接收人

| 类型 | 触发 | 接收人 | 目标 |
|---|---|---|---|
| application.received | 提交申请 | 当前有审批权限的社长/管理员 | 成员管理审批页签；已处理不再提醒审批 |
| application.approved / rejected | 审批结果 | 申请人 | 百业主页/本人申请记录 |
| invitation.received | 定向邀请 | 受邀账号 | 邀请处理入口 |
| invitation.accepted / declined | 定向邀请处理 | 邀请发起人，仍有管理权限时 | 成员/邀请记录 |
| assignment.confirmed | 报名/指派占位成功 | 被排班账号 | 场次详情 |
| assignment.waitlisted | 进入候补 | 报名账号 | 场次详情，明确尚未占位 |
| assignment.removed | 取消/被移出排班 | 原排班账号 | 场次详情 |
| assignment.promoted | 候补递补 | 递补账号 | 详情，保留报名时选择的角色 |
| raid.changed / cancelled | 场次变化/取消 | 受影响的正式与候补账号 | 最新详情/取消后只读详情 |
| raid.reminder | 开打前 N 分钟 | 当前有效正式排班成员 | 场次详情；候补不发 |
| guild.owner_transferred | 转让完成 | 原社长、新社长 | 当前可访问百业页 |

事件保存必要的目标账号/成员关系快照，管理员提醒消费时重查当前权限。结果通知发给事件确定的申请人/受邀人，不用修改后的成员列表猜测接收人；生成前还要确认账号和关联资源未被删除、相关成员关系未失效，删除后不能凭事件快照重新生成旧通知。

创建空场次、复制邀请码不群发；撤回申请、撤销邀请、主动退出、任免管理员保留审计，额外广播不纳入一期。Toast 是操作反馈，持久通知记录仍需真实接口。

审计只在相关数据仍存在时保留，硬删除时一并清理。换角色/定位通过取消后重新报名生成对应 removed/confirmed/waitlisted，不再有 assignment.changed。退会/移出/解散不生成持久通知重新保留已删除对象，仅清理对应业务记录后发送实时刷新提示。

## 3. 提醒配置

百业与场次仅保存 `reminder_enabled, remind_minutes`；默认开启、提前 30 分钟，允许范围 1..1440。新场次复制百业默认，开始前可单独修改；后改百业默认不覆盖旧场次。

开打前生成条件：场次开启提醒、正式排班/成员有效、场次未取消、当前尚未开始。不存在渠道交集、邮箱验证或个人邮件偏好判断。

关闭开打提醒不影响申请、审批、邀请等即时站内通知。配置变化不删除通知，已读与是否生成不同；退会/解散/注销则按作用域硬删除相关通知，不保留历史摘要。

## 4. 架构与数据

```text
业务事务 → 业务数据 + Outbox
                         │
                  OutboxProcessor
                         │ 接收人/模板/去重
                  PostgreSQL notifications
                         │ 事务提交后
                  SignalR → 本人在线连接收到变更提示
                         │
                  REST 查询 → 通知中心/角标
                  （首次连接、重连、重新聚焦也补查）

场次创建/修改 → Outbox → Quartz（PostgreSQL）
                                │ 到期
                         读取最新正式名单
                                │
                         事务写站内通知
```

OutboxProcessor 负责消费，NotificationService 负责接收人/模板/写入，ReminderScheduleService 和 RaidReminderJob 负责调度，NotificationQueryService 负责查询和已读。NotificationHub 管理实时连接，服务通过 IHubContext 在事务提交后向本人连接推送提示。不设业务 MailSender、渠道适配器或投递 Dispatcher。

| notifications 字段 | 用途 |
|---|---|
| id / user_id | 通知与接收账号 |
| type / source_event_id | 类型及事件追踪；纯定时提醒可不关联 Outbox |
| guild_id / event_id / related_user_ids | 清理作用域与涉及账号，业务写入时填充并建立索引 |
| payload | 模板版本、必要变量、内部 target |
| dedupe_key | 唯一逻辑通知键 |
| read_at | 空为未读，非空为已读 |
| created_at | 可见通知生成时间 |

不保留 channel、sent_at、邮件 status、attempts、lease 等投递字段；站内记录事务提交即存在，无需“发送成功”状态。生成任务的重试属于 Outbox，不属于通知条目。

未读部分索引 `(user_id, created_at, id) WHERE read_at IS NULL`；列表稳定排序 `created_at DESC, id DESC`。所有查询和已读仅限本人。

即时去重键 `outbox:{outbox_event_id}`；开打提醒 `reminder:{event_id}:{user_id}`。已生成的同场同账号提醒不因改时重复创建，变化由独立 raid.changed 解释。

## 5. 事务、调度与恢复

- 业务变更与 Outbox 同事务，回滚不产生通知。业务写入、硬删除及任务消费者共用 PostgreSQL 事务级 advisory lock。
- Quartz 周期任务每 10 秒消费到期 Outbox，每批 100 条。通知插入、去重及 processed 标记同事务提交；当前单实例不使用租约或 SKIP LOCKED。
- 消费前检查账号有效和邮箱已验证、百业/场次未删除；面向管理人的申请/邀请结果还检查当前管理权限。删除事务清理相关 Outbox，旧快照不能重新生成已删业务。
- 单条格式异常保存尝试次数与指数退避，下次延迟最高 1 小时；数据库故障整轮回滚，下轮重试。负载修复后可继续消费，不记录业务正文。
- Quartz 使用 PostgreSQL 持久化周期任务，不给每个场次创建独立 Job。每轮读取当前设置、开始时间和正式排班，改时、关闭和取消通过最新数据立即生效。
- 到期提醒只生成开始前当前有效正式成员的记录；同场同账号固定键去重。晚报名在下一轮开始前扫描补查，通常不超过 10 秒，不宣称精确毫秒投递。
- 已开始场次不补提醒。重启或 Misfire 后仍检查实时状态、成员资格和去重。查询优先选择尚有待提醒正式成员的场次，避免已处理场次占满扫描批次。
- 新通知、已读与硬删除提交后用短超时向本人在线连接推送 notifications.changed；发送失败不回滚业务，首次连接、重连、聚焦及断线 REST 补查恢复状态。
- 退会/移出删除本人本百业关联通知和事件，解散删除百业全量，注销删除本人全量；创建模板/场次被清理时其他接收人的关联记录一并删除。不通过持久通知重新保留已删对象。
- 任意时间硬删除，已开始场次不触发候补递补。当前无每场 Job，因此无孤立场次 Job 清理；注销 Redis 会话清理边界见《06-后端开发进度》。

## 6. 接口与前端

全部加 `/api/v1`，要求正式登录且已完成邮箱绑定。

| 方法 | 路径 | 请求/返回 |
|---|---|---|
| GET | /notifications?cursor=&limit=&unread_only= | 本人 items、next_cursor |
| GET | /notifications/unread-count | unread_count |
| POST | /notifications/read | notification_ids 或 all=true；updated_count、unread_count |
| GET / PUT | /guilds/{guild_id}/reminder-settings | reminder_enabled、remind_minutes、expected_version |
| PATCH | /guilds/{guild_id}/events/{event_id} | 单场提醒配置、expected_version；开始前且有管理权限 |

条目示例，实际外层为 `{ data, error }`：

```json
{
  "id": "UUID",
  "type": "assignment.promoted",
  "title": "你已从候补进入队伍",
  "body": "周三固定团已为你安排输出位，请查看本场角色与时间。",
  "created_at": "2026-10-13T10:00:00Z",
  "read_at": null,
  "target": { "kind": "raid_event", "guild_id": "UUID", "event_id": "UUID" }
}
```

target 仅使用平台内已知路由，不接受任意 URL 或执行 HTML。用户仅能读取尚未清理的本人通知，跳转仍校验当前权限；资源已删除返回 404。邀请使用独立 `/invitations/code/[code]` 或 `/invitations/[id]` 页面，本人申请记录与撤回进入 `/settings/applications`，具体设计见《前端设计》7.4。

单条已读用 IDs 长度 1，批量最多 100；all=true 仅标记本次已存在的本人未读记录，不误标之后新通知。轻量查询分别管理列表和角标，已读成功刷新二者；账号切换清理上下文。

一期通知使用 SignalR 提示、分页列表和重新聚焦刷新；连接正常时取消固定角标轮询，连接失败/断线时降级为每 30 秒刷新列表与角标，不可见时暂停降级轮询。恢复连接后立即补查，再停止轮询。不以演示的共享布尔值替代逐条 read_at。个人设置和场次设置移除邮件开关、渠道选择。

### 6.1 SignalR 连接与事件契约

| 项目 | 契约 |
|---|---|
| 服务端 | ASP.NET Core SignalR 的 NotificationHub，与 API 同进程 |
| 端点 | `/hubs/notifications`，同域；独立于 `/api/v1` REST 清单 |
| 客户端 | `@microsoft/signalr`，正式接入时安装，当前演示未接入 |
| 服务端事件 | `notifications.changed`，载荷 `{ "reason": "created" }`、`{ "reason": "read" }` 或 `{ "reason": "deleted" }` |
| 接收范围 | 服务端从已验证 JWT 的 sub 确定 user_id，通过 Clients.User 推送到本人所有标签页/设备连接 |
| 查询与已读 | 保持现有 REST 接口，Hub 不暴露业务写入方法或任意用户/百业订阅方法 |

事件只提示缓存失效，不包含通知正文、名单或未读数快照；客户端收到重复提示仍可安全重新查询。不按提示次数累加角标，列表/角标始终以接口返回为准。Hub 契约单独维护，OpenAPI 只生成 HTTP 接口类型。

- 前端在 `/me` 确认账号 active 且已验证邮箱后，为每个标签页建立一个连接，避免页面/组件各建连接。服务端 Hub 使用 JwtBearer 和 VerifiedEmailRequired，IUserIdProvider 明确映射到唯一账号 sub；客户端不能指定接收 user_id。
- 推送前确认接收账号仍存在且 active；注销账号不再接收提示，不能因已有连接就继续投递。客户端注销成功广播到本人其他标签页，停止旧连接/查询；若注销发生在其他设备，旧页下次调用接口时因账号不存在被拒绝并清理登录态。
- 使用 SDK 的 accessTokenFactory 获取当前内存 Access Token。浏览器 WebSocket/SSE 握手受浏览器 API 限制，SDK 可能将 access_token 放入查询参数；仅 `/hubs/notifications` 的连接请求允许此例外。必须使用 HTTPS/WSS，JwtBearer 的 OnMessageReceived 仅在该 Hub 路径及其子路径读取参数，代理、应用和追踪日志均屏蔽该参数。普通业务 URL、页面跳转禁止携带 Token，Refresh Token 永不进入 Hub、URL 或客户端内存。
- 配置 CloseOnAuthenticationExpiration=true，Token 到期关闭连接。前端复用统一刷新协调器，获取新 Access Token 后重连；accessTokenFactory 不会更新已建立连接的认证身份。首次 start 失败也要退避重试，自动重连用有上限的退避，最终失败继续降级轮询；401 不无限重试，403/EMAIL_BINDING_REQUIRED 停止连接并进入对应处理。
- 首次成功连接、重连、网络恢复和页面重新聚焦均重新查询通知列表与角标；事件使这两类查询缓存失效。已读 REST 提交后也推送 reason=read，使同账号其他标签页和设备更新。异步回调与查询结果必须核对当前账号，防止账号切换后写入旧数据。
- 退出或切换账号先停止旧连接、取消旧重试/降级轮询并清理缓存，再启动新账号连接。默认退出只撤销刷新会话，已有 JWT/连接的服务端有效期边界仍遵循认证方案；若以后要求立即断开所有设备，再建设主动撤销。
- 一期单 API 实例，不启用 Redis backplane。多实例时再启用 SignalR Redis backplane 并配置连接协商所需的会话亲和；backplane 只转发在线提示，不提供离线消息持久化。反向代理同时转发 Hub 协商和连接请求，支持 WebSocket Upgrade 及长连接超时，验证 SDK 回退传输可用。

一期仅覆盖通知实时刷新，不扩展为聊天、在线状态或排班协作广播。排班页保持既有轮询及重新聚焦刷新。

## 7. 注册邮件的边界

当前邮件服务由 Auth 的 `IVerificationEmailSender` 调用 Resend，只负责邮箱注册验证码；QQ 首次绑定暂缓。邮箱密码登录、申请/审批、排班、提醒和通知已读均不发送邮件。

验证凭证的目的、邮箱和 QQ 绑定时的 user_id 必须匹配，Redis 保存哈希、TTL 与尝试次数；发送使用独立限流和短超时。用户可在冷却后重发，供应商失败不表示注册/绑定完成，不将验证码放入业务 notifications 或 Outbox。

一期不建设邮件队列/退避重试后台；先同步调用验证邮件服务，记录脱敏结果，发送失败返回可重试错误。验证码失效重发，账号只在验证通过后完成注册或绑定。SPF/DKIM 等接入要求待服务商确定后按实际配置处理。

## 8. 验收与运行配置

| 项目 | 验证 |
|---|---|
| 权限 | 他人通知 ID 不可读/已读，绑定前业务接口拒绝 |
| 生成 | 业务回滚无通知、重复 Outbox 不重复、接收人正确 |
| 提醒 | 候补不发、递补读取真实角色、关闭开打不影响审批 |
| 变化 | 改时/取消后旧版本失效，晚报名去重，已发不重发 |
| 恢复 | 事务回滚重试、Quartz 周期任务重启补查，不补已开始场次 |
| 前端 | 分页/角标/单条与全部已读、账号切换、手机入口 |
| 实时隔离 | 未登录/未绑定不能连接，用户只接收本人提示，不能指定他人 user_id |
| 实时恢复 | 在线新通知刷新、首次连接/重连补查、推送失败仍可查询、断线降级、Token 到期刷新重连 |
| 多端一致 | 已读同步其他标签页；退出停止旧连接，切换账号不展示旧数据 |
| 硬删除 | 退会/解散/注销通知消失、其他接收人关联通知清理、旧 Outbox/Job 不重建、注销旧连接不继续收到数据 |
| 邮件边界 | 两种验证流程可发送；所有业务动作均不调用邮件服务 |

Notifications/Scheduling 配置模板、默认提前分钟、批大小、Outbox 重试和周期扫描参数；Realtime 配置连接/推送超时及前端重连/降级参数。Auth/Mail 单独配置验证码、限流、供应商/超时；不保留业务邮件投递配置。运行监测增加连接数、重连/推送失败和降级情况，禁止采集 access_token。

当前默认提前 30 分钟，可设置 1..1440；周期扫描 10 秒，晚报名开始前补查。通知没有自动 180 天清理任务，当前只按硬删除范围清理；正常保留期清理可在运维验收时补充。业务只站内，邮件只注册验证，Resend 凭证已配置。
