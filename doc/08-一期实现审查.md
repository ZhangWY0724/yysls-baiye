# 一期实现审查

审查日期：2026-10-13。范围为当前前端路由、API 客户端、业务组件、全局 CSS，以及后端认证、业务事务、通知、查询和现有测试。此次为代码审查，未向正式库写入数据，未发送邮件，未以编译通过替代浏览器验收。

## 优先修复的确定问题

2026-10-13 后端修复更新：下列第 3、4、10、11 项已实施修复，原描述保留用于追踪。创建类幂等支持已补齐；前端其他问题留待前端专项处理。详细变更与验证见《09-后端修复记录》。

1. **P1：共享布局中的会话状态没有完整的账号边界。** `platform-page.tsx` 在进入 login/register 时直接跳过加载，但保留 me；`signIn` 更新 token/epoch，却不通知本标签页的用户资料状态。已登录 A 直接访问登录页并登录 B 后，导航到业务页会先显示 A 的资料；旧 SignalR effect 也可能仍在运行，直到 B 的 me 返回。应以 session identity/version 驱动资料与连接清理，并避免渲染与当前 token 不匹配的 me。
2. **P1：查询失效与并发 GET 合并没有区分读请求代次。** `lib/api.ts` 仅按 epoch/path/headers 合并 GET；写入成功触发 reload 时，如果写入前的同路径 GET 尚未结束，会复用旧请求。结果可能显示写入前数据，直到下一次刷新。必须为写入后失效建立新代次，或等待旧请求后再执行新请求，不能仅靠并发去重。
3. **P1：注册错误与实际账号状态不一致。** `AuthService.RegisterAsync` 先消费验证码、保存账号，后创建 Redis 会话。数据库保存失败会消耗验证码；数据库成功而 Redis 失败会向前端返回注册失败，但邮箱已存在。应把注册成功与自动登录失败分别反馈，并设计验证码/提交失败恢复，不宜跨 PostgreSQL/Redis 假装原子。
4. **P1：通知发送持有全站业务写锁，且 HTTP 响应等待发送。** `NotificationPublisher.FlushAsync` 对每个接收人单独开事务并持有相同 advisory lock，锁内调用 SignalR SendAsync，单人最多等待 2 秒。`BusinessOperations.WriteAsync` 提交后同步等待 FlushAsync。慢推送既拖慢操作响应，也阻塞不相关百业写入；应在提交后脱离业务锁发送，并限制整批耗时。
5. **P2：部分控件箭头样式再次被清除。** globals.css 在 select 的 background-image 之后，又对 `.real-form select`、`.real-card > select`、`.real-inline > select` 使用 background 简写，并重设 padding。这会清除自绘箭头或压缩右侧空间。应统一一个 select 基础规则，拆分 input/textarea，避免后置简写覆盖。
6. **P2：仍有明确的原生控件样式遗漏。** `.real-close` 只有 display/margin，带 class 后又不匹配 `button:not([class])`；副本模板搜索的 Card 直接子 input 不匹配现有表单输入规则。应使用显式 Button/Input/Select 组件或一致 class，减少依赖 DOM 层级与有无 class 的兜底选择器。
7. **P2：通知重连终止后存在无重试路径。** platform-page 的 onclose 调用 refresh；若 refresh 因临时网络/服务错误抛异常，catch 吞掉异常且不安排下次 start，只剩未读数补查。连接可能长期无法自行恢复。应把刷新失败纳入统一退避重连流程。
8. **P2：通用查询的首次失败重试状态不正确。** useQuery 将 loadedPath 仅在成功时更新；首次失败后重试会重新 setLoading(true)，QueryState 卸载已有内容。已有数据背景刷新失败也被 QueryState 整页错误替换，可能卸载编辑表单并丢失未保存输入。应区分首次加载、背景获取和背景错误。
9. **P2：通知页面与业务页面的刷新机制不统一。** 通知变化无差别刷新 /me；通知页操作同时 query.reload 和 changed，再通过 revision 触发 reload；周历固定 30 秒刷新，但打开的 EventDetail 只在聚焦/本人操作时刷新，可能显示旧容量/队伍。应按事件原因和资源键定向失效，并让详情与周历遵循相同策略。
10. **P2：多个列表/周历存在数据库 N+1 查询。** DiscoveryController 每个玩家查询 matching profiles 和默认角色；BusinessViews.MemberAsync 每成员多次查询；EventAsync 每报名者查询角色，周历逐场调用该视图。数据库在远程服务器时，往返次数直接扩大延迟。应按当前页批量读取，再组装 DTO。
11. **P2：失败后的刷新令牌轮换缺少恢复语义。** AuthService.RefreshAsync 在查询 PostgreSQL 账号之前轮换 Redis token，后续数据库故障或 HTTP 响应丢失时，浏览器仍持有旧 token；再次请求会被识别为重放并撤销会话。严格轮换本身合理，但此失败路径需要明确处理和测试，不能把普通故障伪装成登录失效。
12. **P2：网络与代理错误没有标准化。** lib/api.ts raw/csrf 直接 response.json，无超时或取消策略；502 HTML、空响应会暴露 JSON 解析异常，旧页面请求只能忽略结果而无法取消。应统一解析非 JSON 错误、超时和 AbortSignal，且保留会话代次隔离。

## 工程与产品缺口

2026-10-13 前端修复更新：会话边界、GET 写入失效、通知重试/重复刷新、后台错误保留内容、字典缓存及主要样式覆盖已实施；详见《10-前端修复记录》。浏览器控制认证失败，视觉和真实交互验收仍未完成。

- 根布局 RouteShell 直接替换 children，业务 catch-all page 为 null，实际路由都在一个大型客户端 switch 中。此做法绕过常规页面/错误边界组织，继续扩展易出现生命周期问题；应保留共享认证布局，业务内容使用真实页面组件。
- 字典和模板没有明确 stale time：跨页面重复请求字典，RaidsPage 即使未打开模板面板也会请求模板。搜索每次键入立即请求。应按需加载、字典缓存与搜索防抖。
- useAction 以 React busy state 防双击，reload 通常只触发 state 而不返回实际请求 Promise；“操作完成”和“数据刷新完成”混在一起。应明确写入状态、刷新状态和服务端幂等覆盖。
- API 幂等只覆盖场次创建/报名等部分写入，角色/模板/邀请码创建返回丢失后重试可能重复；需按创建类接口明确幂等策略。
- 没有覆盖登录成功后导航、账号切换、通知断线、GET 失效竞争、表单保留和控件实际样式的前端回归测试。已有 9 项基础设施测试是较大流程测试，不能证明所有页面或失败分支正确。
- 尚无生产 HTTPS/反向代理、WebSocket 路径、压测与备份恢复验收；Long Polling 请求持续出现属于当前传输选择，但重复 negotiate/连接 ID 更换仍须单独检查。
- 全球写锁是一期一致性取舍，不等于当前就需要微服务；优先移除锁内网络 I/O 和 N+1，然后用实测决定是否细分锁。
- 按用户明确要求保留任意时间退会/解散、关联硬删除、社长退出即解散、注册邮件限定，不把这些重新列成设计错误。

## 建议推进顺序

先建立前端会话与查询失效的回归验证；修复账号切换、操作后刷新、通知恢复；统一显式基础控件和 CSS；处理注册与刷新失败语义、通知锁内 I/O；批量化查询并检查生产运行配置。每一阶段都以实际操作及请求数量验证，不仅运行 typecheck/build。
